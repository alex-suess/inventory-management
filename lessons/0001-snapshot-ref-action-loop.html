The snapshot, ref, action loop

Lesson 1 · Playwright with Claude · about 10 minutes

Win: you will prompt Claude to drive the inventory app in a real browser, and explain each step it takes.

Recall first

Before reading: what do you already know?

Write down, from memory, how a Playwright script finds and clicks a button. (Locators like getByRole.) Hold that thought: Claude does it differently.

1. Claude does not see pixels

The Playwright MCP server "uses Playwright's accessibility tree, not pixel-based input" (README). The tool browser_snapshot returns the page as text: roles, names and a short ref such as ref=e5 for each element (docs). No vision model is needed.

2. The loop

browser_navigate  -> open a URL
browser_snapshot  -> read the tree, get refs
browser_click / browser_type / browser_fill_form  -> act on a ref
browser_snapshot  -> check what changed

Refs belong to one snapshot. After the page changes, the old refs may be stale, so Claude snapshots again. If a run gets stuck, a stale ref is the first suspect. This is my reading of the docs, not a documented guarantee: verify it in the exercise.

3. Do it

  1. Start the app: run /start in Claude Code. Frontend is http://localhost:3000.
  2. Run /mcp and confirm playwright shows as connected.
  3. Prompt: "Use Playwright to open http://localhost:3000, take a snapshot, and list the filters you find. Then change the Warehouse filter and tell me what changed on the page."
  4. Watch the tool calls (named mcp__playwright__browser_*). Match each one to the loop above.

This repo's .mcp.json pins @playwright/mcp@0.0.37, while the docs show @latest. Tool names can differ between versions, so trust what your session lists.
